# 8D 报告深度研究与 8D Agent 可行性评估

> 结论先行：**做成「小白轻松、熟手更快」的 8D 助手高度可行；做成「一句话自动写出可提交给主机厂的 8D」不可行，且危险。**  
> 正确产品形态不是报告生成器，而是：**证据采集 + 一套案件两种速度 + 门禁式引导/工作台 + 质量评审 + 多模板导出**。  
> 产品原则见 [8D Agent 产品方向](2026-08-30-8d-agent-product-direction.md)。

---

## 1. 8D 报告是什么

8D（Eight Disciplines，八个纪律 / 八个步骤）是一套**团队导向、证据驱动、按门禁推进**的结构化问题解决方法。它不是「填一张表」，而是一套工作流：先保护客户、再找到并验证根因、再永久纠正、再把教训写回管理体系。

输出物通常是一份 1–3 页的 **8D 报告**（客户指定模板），背后应有一整套证据包：Is/Is-Not、5Why、鱼骨图、遏制记录、验证数据、FMEA/控制计划更新等。

**一句话定义：**

> 8D 是汽车供应链（以及航空、医疗器械等高要求行业）处理客诉与重大不合格时的**通用语言**：用固定顺序回答「发生了什么、客户是否已被保护、真正根因是什么、为什么没拦住、永久对策是什么、怎么证明有效、如何防止同类问题再发」。

### 1.1 它解决什么，不解决什么

适合 8D 的场景：

- 客诉、退货、停线、批量不良、安全/法规相关失效
- 根因未知、跨部门、很可能再发
- 客户明确要求 8D / SCAR / 8D-Bericht
- IATF 16949 条款 10.2 下需要结构化纠正措施的记录

不适合（用更轻的工具）：

- 根因已知且已验证的一次性任务
- 低严重度内部轻微不良（用 5Why 或 A3）
- 纯变异削减项目（用 DMAIC）
- 软件事故复盘（时间线 + 5Why 通常更合适）

### 1.2 与相近方法的关系

| 方法 | 来源 | 最适合 | 形式 | 典型周期 |
| --- | --- | --- | --- | --- |
| 8D | 福特 1987 / G8D 1990s | 客诉、供应商不合格 | 客户模板 + 门禁 | 遏制数小时–2 天；闭环 14–60 天 |
| A3 | 丰田 | 内部持续改善 | 一页 PDCA 叙事 | 数天–数周 |
| DMAIC | 六西格玛 | 数据驱动的变异削减 | 五阶段项目 | 3–6 个月 |
| 5Why / 鱼骨图 | 丰田 / 石川馨 | **嵌在 8D 的 D4 里** | 分析工具，不是完整流程 | 30–90 分钟 |

关键点：5Why 和鱼骨图**不是 8D 的替代品**，它们是 D4 的分析引擎。8D 提供工作流包装、客户保护（D3）和体系闭环（D7）。

## 2. 历史与标准谱系

- **1974**：美军 MIL-STD-1520，要求承包商按纪律做纠正措施。
- **1987**：福特发布 *Team Oriented Problem Solving (TOPS)*，即 TOPS-8D，目标是切断「灭火式」质量处理——同一缺陷反复出现，因为从未留下可验证的根因。
- **1990s 中期**：福特加入 **D0（准备 / 紧急响应）**，形成 **Global 8D (G8D)**。
- **之后扩散**：几乎所有主机厂 CSR（Customer Specific Requirements）都要求 8D 或等价物；航空（AS9100 / AESQ RM13000）、医疗器械 CAPA 也广泛采用。
- **IATF 16949:2016 §10.2**：标准**没有点名 8D**，但要求不合格的结构化根因分析、纠正措施与有效性验证。实务上，主机厂 CSR 把 8D 变成了供应链的默认格式。
- **VDA Volume 8D**：德国汽车工业协会标准化投诉处理中的 8D 报告，强调失败原因分类、客户-供应商协同、可追溯文档。
- **主机厂变体**：VW 8D-Bericht（CATS 门户）、Ford G8D、Stellantis SCAR、BMW / JLR / 奔驰各有字段、时效与证据要求。

**对 Agent 的含义：** 产品必须把「方法论内核」和「客户模板外壳」拆开。内核（D0–D8 逻辑、双根因、门禁）可以统一；外壳必须可插拔。

## 3. D0–D8 深度拆解（每个步骤的输入、输出、门禁）

### D0 准备与紧急响应（ERA）

**目的：** 症状刚出现时，先判断要不要上 8D，并立刻保护客户。

**要做的事：**

- 量化症状（不是猜测根因）
- 识别受影响客户 / 批次 / 库存位置（成品、在制、在途、客户现场、售后）
- 必要时立即执行 **Emergency Response Action**（停发、隔离、通知）
- 判断是否满足启动 G8D 的条件：症状可量化、客户已知、绩效缺口存在、**根因未知**、管理层愿意投入资源、复杂度超过单人能力

**门禁：** 没有紧急保护动作就进入「分析」，是专业 8D 里最常见的政治失败。Agent 必须**先问遏制，再问根因**。

### D1 组建团队

**目的：** 跨职能、有权限、有时间、有负责人。

**实务规则：**

- 3–7 人：过程负责人、质量、至少一名现场专家；客诉再加 SQE / 客服 / 物流
- 必须有 Champion（能调资源）和 Team Leader（推进门禁）
- 一人兼职晚上写报告，是 8D 逾期的第一原因

**对小白产品：** D1 可以做成「角色推荐器」（根据问题类型建议该拉谁），但不要假装一个人就能做完整 8D。产品文案必须诚实：**Agent 降低门槛，不替代团队与现场。**

### D2 问题描述（8D 的地基）

**目的：** 用事实画清问题边界。D2 写糊了，后面全部跑偏。

**标准工具：**

1. **5W2H**：What / Where / When / Who / Why（仅初始假设） / How / How many，全部必须可量化。
2. **Is / Is-Not**：什么是、什么不是；哪里是、哪里不是；何时是、何时不是；多少是、多少不是。差异往往直接指向根因。

**合格的问题陈述示例：**

> 2026-04-01 14:00 起，客户 A 工厂 3 线 4 工位来料检发现：左外侧支架焊缘内弯 1.5–2.0°，每班 240 件中 18 件（7.5%）。右侧支架、内侧面尺寸、其他客户、4 月 1 日前批次均未发现。根因未知。

**不合格：** 「支架有质量问题，客户投诉。」

**Agent 关键能力：** 把用户口语投诉改写成 5W2H + Is/Is-Not，并对缺失字段**追问而不是编造**。

### D3 临时遏制（ICA）

**目的：** 在根因未知时保护客户。这是客诉场景里**时限最死**的一步，通常 24–48 小时（部分德系门户更短）。

**有效遏制：** 100% 分选、停发、隔离、第三方分选、临时加检、返工（需客户批准）、已检库存重新放行、必要时现场更换。

**两条铁律：**

1. 遏制必须**验证有效**（抽检/全检数据），不能只写「计划中」。
2. 遏制是临时的。永久对策验证通过后必须撤掉。把 100% 全检当永久对策，是退件重灾区。

### D4 根因与流出点（分析心脏）

必须找出并验证**两个根因**：

| 类型 | 问题 | 若不做会怎样 |
| --- | --- | --- |
| **发生原因 Occurrence** | 为什么做出了不良？ | 源头还在，遏制一撤就复发 |
| **流出原因 Escape** | 为什么检测系统没拦住？ | 下一次同类变异仍会流到客户 |

**标准工作流：**

1. 鱼骨图 6M（人/机/料/法/环/测）铺候选原因
2. 用 D2 的 Is/Is-Not 筛掉解释不了「为什么不是那边」的假说
3. 对最可能分支做 5Why，追到**系统层**（标准、防错、维护制度），而不是「弹簧坏了」
4. **验证**：复现、关掉/打开该因子、数据对照。未验证的根因只是猜测
5. 单独找 **Escape Point**：过程中本应检出却未检出的那个控制点

**绝对禁区：**

- 「操作工疏忽 / 质量意识不足」不是根因
- 「供应商来料差」不是根因（要问：为什么 IQC/过程允许它进来）
- 5Why 停在第 2–3 层（表面原因）

### D5 选择并验证永久纠正措施（PCA）

对发生原因和流出原因**各选一条永久对策**，并在实施前验证「将会有效且无副作用」。

**对策强度层级（从强到弱）：**

1. 消除失效模式（设计上不可能发生）
2. 替换更稳健的材料/工艺/供方
3. 工程控制 / 防错（Poka-yoke）
4. 管理控制（SOP、培训、制度）
5. 警示 / 双人复核（最弱）

「再培训操作工」几乎总应被挑战。培训可以是 D7 的配套动作，不能当 D5 的主对策。

### D6 实施并验证有效性

三件事：上线 PCA → 用数据监控（常见：连续 30 天 / 前三批 / 规定批次数不良为 0，视客户 CSR）→ **撤掉 D3 遏制**。

数据回来了就不是 D6，要退回 D4。不允许「效果良好」这种空话。

### D7 防止再发（最常被跳过、价值最高）

把个案变成体系默认：

- 更新 PFMEA（Detection 评级、新增控制）
- 更新控制计划
- 修订作业指导书 / 点检表 / PM 计划
- 培训与考核记录
- 横向展开：同类产品、同类设备、其他工厂、在研项目 DFMEA
- 若是供方原因，推到同类供方，不只这一家

没有这些**制品**的 D7，等于没做。

### D8 表彰团队与关闭

正式致谢、沉淀 lessons learned、质量经理会签、与客户 SCAR 号索引、按产品寿命归档。文化步骤，也是知识不流失的步骤。

## 4. 一份「能过客户关」的 8D 长什么样

客户 SQE / 审核员真正看的不是文采，是**证据链**：

```
症状照片/数据 → 量化 D2 → 已执行且有效的 D3
    → 双根因（发生+流出）+ 验证实验
    → 与根因一一对应的 PCA（不是加检）
    → 改善前后数据
    → FMEA/CP/SOP 更新与横向展开清单
```

### 4.1 高频退件原因（Agent 必须内置拦截）

1. D2 一句话、无数量/批次/位置
2. D3 写成「将于某日完成」，而不是「已于某日完成，拦截 N 件」
3. 把遏制当纠正（D5 仍是 100% 全检 / 加强巡检）
4. 只写发生原因，漏流出原因
5. 根因停在人：操作工、培训、意识、处罚
6. 5Why 逻辑断裂或跳层
7. D6 无数据（「效果良好」）
8. D7 空泛，无文件编号/版本/横向清单
9. 一个 8D 里塞多个无关失效模式
10. 关闭时 D3 仍在运行（说明根因可能从未被消灭）

### 4.2 时效（因客户而异，产品要可配置）

| 节点 | 常见要求 |
| --- | --- |
| 紧急响应 / 接收确认 | 部分德系门户：数小时级（有资料称 VW CATS 初始反应极短） |
| D3 遏制 | 普遍 24–48 小时；日系常更严 |
| 含初步原因的中间 8D | 常见 72 小时–10 个工作日 |
| 完整闭环 | 14–21 天（部分日系）到 30–60 天（欧美常见） |
| 效果验证 | 改善后 7 个工作日 / 前三批 / 30 天干净产量 等 |

IATF 本身不定死天数，**客户 CSR 才定死**。Agent 必须按「客户档案」加载时效，而不是写死一套。

## 5. 小白为什么写不好 8D（产品要解决的真实痛点）

工厂一线的典型用户不是资深质量经理，而是：

- 刚转岗的 QE / 应届生
- 被客户催报告的生产主管
- 一人身兼多职的供应商质量员

他们的障碍不是「不会用 Word」，而是：

1. **把 8D 当成作文**：先有结论再填格子
2. **不懂三个措施层**：紧急响应 ≠ 遏制 ≠ 永久纠正 ≠ 预防
3. **不会提问**：不知道 D2 缺了哪些事实
4. **不会验证**：把脑暴当根因
5. **怕现场**：不愿去三现（现场、现物、现象）
6. **模板恐惧**：每个主机厂表格不一样
7. **时间压力**：24 小时先交 D3，来不及「学方法论」

因此，对小白友好 **≠ 替他编造一份看起来专业的报告**。  
对小白友好 = **用普通话问对的问题、挡住错的写法、把专业结构藏进向导里**。

## 6. 市场与竞品：AI 8D 已经存在，但大多走错形态

已观察到的产品形态：

| 类型 | 代表 | 优点 | 致命弱点 |
| --- | --- | --- | --- |
| 一键生成完整 D0–D8 | 8D.wiki 等 | 3 分钟出 PDF，小白体感爽 | 极易幻觉根因与数据；审核必挂 |
| 对话式质量同事 | QualityOS | 先遏制后根因、OEM 格式、逐步提问 | 仍是 SaaS；中文/国产主机厂覆盖弱 |
| 传统 QMS 工作流 | Omnex、Mobile2b 等 | 任务、时效、审计轨迹 | 重、贵、对小白不友好 |
| Excel/PPT 模板 | 满网都是 | 零成本 | 不教思考，复制错误 |

**空白机会（尤其中文市场）：**

- 国产/日系/自主品牌主机厂模板与话术（比亚迪等「2458」类时效：24h 临时方案、48h 改善措施、5 天正式 8D、8 天验证等——具体以各客户 CSR 为准）
- **硬门禁**：禁止未验证根因进入 D5；禁止「培训/加检」作为唯一 PCA
- 照片/检验数据/工艺文件上传后的**证据绑定**，而不是纯文本生成
- 把「教 8D」和「写 8D」合成一个产品：做完一个真实案例，人也会了

## 7. 可行性评估

### 7.1 总评

| 能力层 | 可行性 | 说明 |
| --- | --- | --- |
| 把口语投诉结构化为 D2 | **高** | LLM 擅长补全提问与改写；禁止补造数字 |
| 推荐遏制清单（D3） | **高** | 有限模式（分选/隔离/停发/在途/客户现场），规则+LLM |
| 引导 5Why / 鱼骨图 | **中高** | 可教练；不能代替现场验证 |
| 自动「发现」真实根因 | **低** | 根因在工厂里，不在模型权重里 |
| 生成专业中文/英文报告与多模板 | **高** | 结构化数据 → 模板渲染是工程问题 |
| 自动通过主机厂审核 | **低（且不该承诺）** | 责任必须留在质量工程师 |
| 小白 30 分钟独立完成可用初稿 | **中高** | 前提是用户能提供事实与照片；D4/D6 仍需现场 |

**综合判断：** 作为 **人机协同的 8D 教练 + 报告编译器**，技术成熟度足够，商业上有真实刚需（客诉时效 + 人才缺口）。作为 **全自动问题解决 AI**，既不诚实也不合规。

### 7.2 为什么「一键生成」会害用户

LLM 会写出语法正确、结构完整、看起来很 8D 的文字，例如：

> 根因：操作工未按 SOP 作业。纠正：加强培训与巡检。预防：提高质量意识。

这正是客户退件模板。若产品优化目标是「完整率/速度」，它会系统性生产**不合格专业外观**。对小白更危险：他们无法识别幻觉。

所以产品成功指标不能是「生成速度」，必须是：

- 门禁拦截率（拦住了多少禁区写法）
- 字段完整率（5W2H / 双根因 / 验证证据）
- 人工修改量（越少说明引导越准）
- 模拟 SQE 评审通过率（用规则+模型双审）

### 7.3 技术可行性拆分

**已经很容易的部分：**

- 对话式收集 5W2H
- 将结构化 JSON 渲染为 Word/PDF/Excel
- 多语言（中/英，客户邮件口吻）
- 检查清单、时效提醒、进度条 D0→D8
- 对草稿做「假 8D」检测（规则为主）

**需要精心设计的部分：**

- 状态机：未满足门禁不能进入下一步，但允许「先交 D3 中间版」
- 证据对象模型：每条措施绑定负责人、时间、数量、附件
- 双根因并行向导
- 5Why 质量评分（是否触及系统层、是否循环、是否归咎于人）
- 客户配置包（模板、时效、禁用词、必填证据）

**现在不要做的部分：**

- 声称对接所有主机厂门户自动提交
- 无现场数据的根因「预测」
- 自动改用户的 FMEA 主文件（最多生成「建议修订清单」）

### 7.4 合规与责任

- 8D 是客户正式记录，错误报告可导致索赔、升级、Wiederholfehler（重复失效加倍考核）
- 产品必须：**人是责任主体，AI 是起草与质检**
- 导出页应有「待验证字段」水印；未验证根因不得标为 Closed
- 工厂数据敏感：默认本地/私有化路径要比「把客诉丢进公有模型」更可信

## 8. 三种产品路径（含取舍）

### 方案 A：聊天包装器（不推荐做主产品）

用户说「帮我写 8D」，模型一次吐出 D0–D8。

- 优点：一周能做出来，演示好看
- 缺点：幻觉、教坏小白、无法对客户负责
- 定位：最多当「演示原型」，不能当交付物

### 方案 B：一套案件、两种速度（推荐）

同一份结构化 Case：小白走问答向导，熟手走整页工作台；讲解可折叠，门禁不因人放松。事实由用户确认；模型负责抽取、改写、检查、套模板；最后从结构化数据生成专业报告。

- 优点：同时服务两种人；把重复劳动（格式、翻译、缺项、换皮）拿走，把现场与验证留给人
- 缺点：交互要做渐进披露，比「纯聊天」或多一张工作台
- 工作量：方法论引擎 + 双速度 UX + 模板 + 评审器，MVP 边界仍然清晰

### 方案 C：嵌入 QMS 的企业平台

案件、任务、升级、FMEA 联动、供应商门户。

- 优点：客户愿意付年费
- 缺点：重、实施周期长、不是「小白轻松用」的第一刀
- 建议：作为方案 B 验证后的第二阶段，而不是起点

**推荐：方案 B。** 对话向导给小白，工作台给熟手，规则引擎做骨，人确认做肉。详见产品方向文档。

## 9. 推荐产品设计（方案 B 纲要）

### 9.1 用户体验原则

1. **先保护客户，再分析原因**（顺序写死）
2. **一套案件，两种速度**：小白默认向导，熟手默认工作台；讲解可折叠，门禁不放松
3. **一次一个问题**（向导），选项优先于开放题；工作台允许整页粘贴
4. **不懂就给例子**，不给质量黑话考试
5. **缺数据就停下来要证据**，绝不脑补 PPM、批次、日期
6. **随时可导出「中间 8D」**（标清哪些是草稿/待验证）以满足 24h 时效
7. **内置反对意见**：用户写「加强培训」时，Agent 必须追问系统原因
8. **重复的自动化，核心的留给人**：格式/抽取/检查/换模板交给工具；现场、验证、拍板留给团队

### 9.2 核心对象

```
Case
  customer, part, defect, severity, sla_profile
  team[]
  problem: 5W2H + is_is_not
  containment[]          # D3，含验证数据
  occurrence_rca         # 5Why + 验证
  escape_rca             # 5Why + 验证
  pca[]                  # 与根因一一对应
  validation             # D6 指标与结果
  prevention[]           # 文件更新 + 横向展开
  evidence[]             # 照片、表格、实验
  review_findings[]      # 内部 SQE 模拟评审
```

报告 = 对象的投影，不是聊天记录的摘要。

### 9.3 Agent 角色（不要做成一个万能聊天机器人）

| 角色 | 职责 |
| --- | --- |
| 引导员 | 按状态机提问、解释这一步为什么存在 |
| 结构化书记员 | 把回答写入对象，标出冲突与缺口 |
| 红队评审 | 用退件清单打分，阻止进入下一步 |
| 撰稿人 | 只在数据完整后生成客户语言（中/英） |
| 模板渲染 | Word/PDF/Excel，OEM 皮肤 |

### 9.4 小白路径（主成功场景）

1. 粘贴客户投诉 / 上传不良照片
2. Agent 抽出已知事实，列出「还缺什么」
3. 10 分钟完成 D0–D3 中间版 → 导出给客户挡第一枪
4. 引导去现场收集 Is/Is-Not 与候选原因
5. 教练 5Why（双链），每层提供「还不够深」的反问
6. 用户贴上验证数据后才解锁 D5
7. 对策按强度层级排序，拦截纯检验/纯培训
8. 生成 D7 检查清单（FMEA/CP/SOP/横向）
9. 内部评审报告：红/黄/绿 + 修改建议
10. 导出专业 8D + 证据附录

### 9.5 MVP 范围（做窄才能做对）

**做：**

- 通用汽车供应链 8D（中文主界面，中英导出）
- D0–D8 状态机 + 退件规则
- 5W2H / Is-Is-Not / 双 5Why
- 中间版 + 终版 PDF/Word
- 一个高质量通用模板 + 一个「客户字段映射」扩展点

**不做（第一期）：**

- 自动提交 CATS / 福特门户
- 全自动根因推断
- 复杂 FTA / DOE
- 多租户 QMS、权限矩阵、供应商协同（可第二期）

## 10. 风险与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| 幻觉事实 | 索赔、客户信任崩溃 | 事实字段只读自用户确认；生成层禁止发明数字 |
| 教坏小白 | 短期爽、长期退件 | 红队评审 + 禁区词 + 强制双根因 |
| 把团队方法做成单人工具 | 报告脱离现场 | D1 角色提醒；关键步骤要求「现场确认」勾选 |
| 模板碎片化 | 永远做不完 OEM | 内核/外壳分离；先通用 + 3 个最高频模板 |
| 隐私 | 客诉含客户名、缺陷率 | 私有化/企业 API；默认不把附件用于训练 |
| 过度承诺「专业」 | 法律与口碑 | 明确：辅助起草，关闭权在持证质量人员 |

## 11. 最终判断

**要不要做？要做。** 8D 有稳定刚需、强时效、人才缺口大，且现有「一键生成」产品在专业性上留出了空位。

**做成什么样才算成功？**

> 小白被领着走完，熟手自己跑得更快；抬头信息、改写、套模板、缺项自检从小时级降到分钟级；省下的时间用在现场确认和根因验证上。终稿仍然挡得住「操作工 + 加强培训」这种假闭环。

**什么叫失败？**

> 三分钟生成排版精美、内容虚构的 PDF；或把熟手当小白训、把小白扔进空白大表。

8D Agent 的护城河不在文笔，在**门禁、证据模型、评审标准，以及把重复劳动从核心工作里拆出去的能力**。
